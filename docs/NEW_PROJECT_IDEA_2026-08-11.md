## 1. 왜 방향을 바꾸는가 — 픽앤조이 진단

### 1-1. 구조적 문제

| 항목 | 현실 |
|---|---|
| 시작 방식 | 강의를 따라 만듦. 자체 기획 없음 |
| 도메인 | "픽앤조이" 검색 시 **공구 판매**가 상위 점유 |
| 콘텐츠 | AI 생성. 사진 수·경험·현장감 부족 |
| 투입 비용 | 100만원+ (API 폭탄 다수 포함) |

### 1-2. 콘텐츠별 자체 평가

| 카테고리 | 평가 | 근본 문제 |
|---|---|---|
| 맛집 | **낮음. 서비스 안 해도 될 수준** | 가본 적 없는 곳. 사진·평점이 Google Places 인용 |

| 인천시 | 나쁘지 않음 | 공공 API 재가공. 원본이 정부 사이트에 존재 |
| 전국보조금 | 나쁘지 않음 | 동일 |
| 축제 | 나쁘지 않음 | 동일 |

### 1-3. 핵심 진단

**2,255페이지가 있지만, 그중 어느 것도 "여기서만 볼 수 있는" 것이 아니다.**

Google 입장에서 "왜 원본 대신 여기를 보여줘야 하는가"에 답이 없다.
AdSense가 반려하는 대표 사유인 "낮은 가치의 콘텐츠"에 구조적으로 걸린다.

### 1-4. 대조 사례 — 강사의 사이트

- 전 세계 AI 순위를 매일 체크해 제공
- UI 허접, 규모 작음
- **그럼에도 AdSense 빠르게 승인**

차이는 품질이 아니라 **편집의 독창성**이었다.
"다른 어디에도 없는 형태로 정리한 것"이 있었다.

### 1-5. 비용 구조의 근본 차이

| | 픽앤조이 | 지향점 |
|---|---|---|
| 콘텐츠 | 하루 24페이지를 **돈 주고 생산** | 작업하다 보면 **자동으로 생김** |

**픽앤조이는 Roy를 위해 일하지 않는다. Roy가 픽앤조이를 위해 일하고 있다.**

## 2. 참고 사례 — BlogHub (2026-08 GeekNews)

### 2-1. 무엇을 했나

자체 구축(백엔드~프론트 직접 제작) 개발자 블로그만 모아
원본 링크로 트래픽을 보내주는 허브. 등록 폼으로 자발적 참여.

### 2-2. 왜 창의적인가

**콘텐츠를 만든 게 아니라 연결을 만들었다.**

| 요소 | 내용 |
|---|---|
| 문제 | 자체 구축 블로그는 좋은 글을 써도 고립됨 |
| 통찰 | 흩어진 것을 모으면 서로에게 트래픽이 생김 |
| 실행 | 허브 + 등록 폼 + 원본 링크 |
| 콘텐츠 | **본인이 안 씀. 남의 글을 모음** |
| 원가 | 거의 0 |
| 성장 | 등록자가 각자 링크를 검 → 자가 증식 |

### 2-3. 성립 조건 (일반화)

1. **흩어져 있는데 모을 곳이 없다**
2. **모으면 당사자들이 이득을 본다** (그래서 자발적으로 등록)
3. **만드는 사람이 그 판을 직접 겪었다**

3번이 관건. BlogHub 제작자는 본인이 자체 블로그 운영자였다.
**직접 겪은 불편이 아니면 무엇을 모아야 할지 모른다.**

### 2-4. 검증된 접근법

- MVP를 먼저 만들고 **GeekNews에 올려 반응을 봄**
- 사이트를 완성하고 나서 수요를 묻지 않았다
- 같은 날 유사 서비스(Indieblog)가 올라온 것을 보고 "니즈가 확실하다"고 판단

**이것이 픽앤조이에서 하지 못한 것이다.**
5개월 만들고 나서 "이게 될까"를 묻고 있다. 순서를 뒤집는다.

### 2-5. 검토했으나 기각한 방향

| 방향 | 기각 사유 |
|---|---|
| 철학관·역술인 허브 | **이미 포화.** 무당/역술인 묶는 서비스 다수 존재 |
| 실패 기록 **허브** | 모을 원천이 부족. 쓰는 사람이 거의 없음 |

→ 허브형은 원천이 있어야 성립한다. 없으면 **직접 쓰는 쪽**으로 간다.

## 3. 핵심 아이디어 — AI가 못 알려주는 것

### 3-1. 정의

| 유형 | 예시 |
|---|---|
| **최근에 바뀐 것** | Reuters/AP가 무료 RSS 중단. Netlify가 크레딧제로 전환 |
| **문서에 없는 것** | Cloudflare Pages 배포당 파일 20,000 제한 (요금제 요약에 없음) |
| **해봐야 아는 것** | `prefetch={false}`는 파일 수를 줄이지 않는다 (실측 0) |
| **AI가 틀리는 것** | 낡은 요금 정보를 현재형으로 단정 |

### 3-2. 왜 이것이 유효한가

AI는 학습 시점 이후를 모르고, **모른다고 말하는 대신 옛날을 현재형으로 말한다.**

> 2026-08-11 실사례: Claude가 "Netlify는 파일 수 제한 없음"이라고 답변.
> 실제로는 2025년 9월 크레딧제 전환으로 **매일 배포만으로 무료 한도 초과**.
> 1년 전 정보를 현재형으로 말한 것.

이 영역은 **검색해도 안 나오고 AI도 못 알려준다.**
직접 부딪힌 사람만 안다.

### 3-3. 시장 조사 결과 (2026-08-11 검색)

**있는 것**

| 유형 | 예 |
|---|---|
| 일반론·칼럼 | "AI 코드는 신입 코드처럼 리뷰하라" — 원칙만 |
| 대형 사고 사례집 | 질로우 3억 달러 손실, MS 챗봇 Tay — 남의 얘기 |
| 단발성 실패 후기 | "AI 길들이기 실패했습니다" — 커뮤니티 글 1편 |
| 유형 정리 | AI 글쓰기 6가지 실패와 가드레일 — 주제 한정 |

**없는 것**

> **하나의 프로젝트를 끝까지 따라가며 실패와 규명 과정을 축적한 곳**

검색된 글은 전부 단발이다. "이런 실패가 있었다" 한 편으로 끝나거나,
원칙만 나열하거나, 남의 대형 사고를 모아놓았거나.

**⚠️ 주의**: 검색 결과가 적다는 건 "아무도 안 썼다"일 수도,
"읽는 사람이 없다"일 수도 있다. **§7의 테스트로 확인할 것.**

### 3-4. 차별점

Roy가 가진 것:

- **같은 프로젝트 5개월치 연속 기록** (픽앤조이 3월~, Trading V2 6월~)
- 함정 18개가 **실측 근거와 함께** 정리됨 (`PROJECT_CRITICAL_NOTES.md`)
- **실패한 가설과 왜 틀렸는지**까지 기록 (2026-08-10 하루에만 6건)
- 커밋 해시·로그 수치 같은 **1차 자료**

**업계 통념과 정반대라는 점도 차별점이다.**
일반적인 AI 에이전트 메모리 설계는 "성공의 역사만 기록하고 실패는 배제"를 권한다.
Roy는 반대로 **실패를 기록해서 재발을 막는다.** 그리고 실제로 작동한다.

## 4. 실전 재료 — 이미 확보된 것

### 4-1. 픽앤조이 (2026-03 ~ )

#### ⭐ RSC payload 사건 (2026-08-06 ~ 08-11) — 최우선 소재

**서사가 완결돼 있고 실측 수치가 전부 있다.**

| 단계 | 내용 | 수치 |
|---|---|---|
| 증상 1 | 배포 3일 중단. **Actions는 초록불, 텔레그램 정상 리포트** | — |
| 원인 1 | 파일 수 한도 초과 + 가드가 `exit 0`으로 스킵 | 20,340 / 한도 20,000 |
| 오대응 | 와일드카드 `__next.*.txt` 일괄 삭제 | 20,340 → 2,425 |
| 증상 2 | 나흘 뒤 번호 페이지네이션 전환 → **전 페이지 다운** | — |
| 오진단 | 4개 가설 연속 실패 | — |
| 진짜 원인 | 네비게이션 필수 payload까지 삭제됨 | — |
| 정정 | prefetch용 2종만 삭제 | 20,347 → 15,865 |
| 무효 확인 | `prefetch={false}` 실측 | 20,347 → **20,347 (감소 0)** |

**핵심 지식**

- HTML 페이지 2,246개 = 실제 파일 20,347개 (**페이지당 6~9개**)
- `.txt` 종류별: `_tree` 2,241 / `_head` 2,241 / `_index` 2,241 /
  `__PAGE__` 2,241 / `<route>` **4,481** / 기타 4,473 — **균등 분포 아님**
- prefetch용(`_tree`/`_head`)과 네비게이션용(`_index`/`<route>`)은 **이름이 비슷하지만 역할이 다름**
- Network 스택으로 구분 가능: prefetch는 `eh`, 실제 네비게이션은 `ep → F → e`

#### 그 외 소재

| 소재 | 내용 |
|---|---|
| 배포 가드 `exit 0` 함정 | 초록불 + 정상 리포트인데 사이트는 3일간 멈춤 |
| Suspense 위치 | 조건 분기 안쪽에 두면 **빌드·타입검사·로컬 전부 통과하고 배포에서만 깨짐** |
| `trailingSlash` 규약 | 규칙을 문서화 안 하면 어떤 AI 모델이든 절반은 틀림 |
| 위음성 검증 | HTTP 200, `pageerror` 0은 아무것도 증명하지 않음 |
| `.wranglerignore` 함정 | wrangler Pages는 이 파일을 안 읽음. `.assetsignore`만 읽음 |
| `public/` dotfile | Next.js가 `out/`으로 복사하지 않음 |
| Cloudflare Zero Trust | `/admin` 라우트 One-time PIN 인증 구성 |
| GitHub Actions 러너 배정 실패 | `if: failure()` 알림이 잡지 못하는 경우 |

### 4-3. 호스팅 실전 비교 (2026-08-11 조사)

**요금제 표에 안 나오는 것들**

| 항목 | 표에 적힌 것 | 실제 |
|---|---|---|
| Cloudflare Pages Free | "unlimited static sites" | **배포당 파일 20,000개 제한** |
| Cloudflare 유료 전환 | "Paid plans" | Workers Paid($5)는 **무관**. Zone Pro($20)여야 함 |
| Cloudflare Pro 적용 | 100,000개 | 환경변수 `PAGES_WRANGLER_MAJOR_VERSION=4` **필수** |
| Netlify Free | "100GB / 300 build min" | **2025-09 크레딧제 전환.** 300 크레딧/월 |
| Netlify 배포 비용 | — | 프로덕션 배포 **1회 = 15 크레딧** (빌드 시간 무관) |
| Vercel Hobby | "무료" | **상업적 이용 금지** |

**픽앤조이 기준 실계산**

```
매일 자동 배포 30회/월 × 15 크레딧 = 450 크레딧
Netlify 무료 한도 = 300 크레딧
→ 대역폭 0으로 잡아도 초과. 초과 시 그달 남은 기간 사이트 정지.
```

**판단 공식**

```
예상 페이지 수 × 7 ≈ 예상 파일 수
이 값이 호스팅 제한의 50%를 넘으면 다른 호스팅 검토
```

**증가 속도 실측 (픽앤조이)**

| 날짜 | 삭제 전 | 삭제 후 | 페이지 |
|---|---|---|---|
| 08-10 | 20,347 | 15,865 | 2,244 |
| 08-11 | 20,453 | 15,949 | 2,255 |
| 증가 | +106 | **+84** | +11 |

→ 페이지당 약 7.6개. 한도(20,000) 도달까지 약 48일.

| 가설 | 왜 틀렸나 |
|---|---|
| RSC payload 404가 원인 | 404 종류를 구분 안 함. 본 것은 전부 prefetch용 |
| 업로드 누락 / 부분 배포 | 정상 배포와 로그 수치 **완전 동일** |
| 파일 수 한도 초과 | 두 배포 모두 2,431개로 동일 |
| sessionStorage 잔여 참조 | 전환 커밋이 이미 깨끗하게 제거함 |
| trailing slash 누락 | 4개월 전 코드. 그동안 정상 동작 |
| `prefetch={false}` | 실측 감소 0 |

**도출된 원칙**

1. 삭제를 제안받으면 **무엇이 지워지는지 종류별로 열거시켜라**
2. AI의 **"무해 확정" 같은 단정을 의심하라**
3. 가설이 **두 번 빗나가면 코드 추론을 멈추고 실측으로 전환**
4. **정상 사례를 확보하고 실패 사례와 하나씩 비교하라** (가장 빠른 경로)
5. 관측 데이터를 뭉뚱그리지 마라. 404가 20개면 **종류별로 나눠서** 봐라
6. 한 번에 하나만 바꿔라. 여러 개를 동시에 바꾸면 원인 특정 불가

## 5. 콘텐츠 방향

### 5-1. 원칙

| 원칙 | 이유 |
|---|---|
| **날짜를 명시한다** | "언제 확인했는가"가 정보의 핵심. 바뀌는 정보이므로 |
| **실측 수치를 넣는다** | 20,347 / 15,865 / 84개 — AI가 못 쓰는 것 |
| **1차 자료를 넣는다** | 로그 원문, 커밋 해시, 스크린샷 |
| **틀린 가설도 쓴다** | "이렇게 접근했는데 아니었다"가 남들의 시간을 아낀다 |
| **해법 없이도 쓴다** | "아직 못 풀었다"도 정보다 |

### 5-2. 안 하는 것

| 안 함 | 이유 |
|---|---|
| 튜토리얼 | 이미 넘침. AI가 더 잘 씀 |
| 프롬프트 모음 | 포화 |
| 일반론 ("AI 코드는 리뷰해야 한다") | 원칙만으로는 가치 없음 |
| AI 대량 생성 | 픽앤조이의 실패를 반복 |
| 매일 발행 | 주 1~2편. 작업하다 나오는 만큼만 |

### 5-3. 예상 글 구조 (샘플)

```
제목: Next.js 정적 사이트, 2,255페이지에서 Cloudflare가 배포를 멈췄다

1. 증상 — 배포 3일 중단, Actions는 초록불
2. 원인 — 페이지 2,246개인데 파일은 20,347개
3. 왜 그런가 — RSC payload 구조 (파일 종류별 표)
4. 잘못된 대응 — 와일드카드 삭제 → 클릭 먹통
5. 올바른 대응 — prefetch용만 삭제 (15,865개)
6. 안 통한 것 — prefetch={false}는 파일 수 안 줄임 (실측 0)
7. 호스팅 3사 비교 — 요금제 표에 안 나오는 것들
8. 판단 기준 — 예상 페이지 × 7 = 파일 수
```

## 7. ⭐ 실행 순서 — 사이트부터 만들지 않는다

**픽앤조이의 가장 큰 실수는 5개월 만들고 나서 "될까"를 물은 것이다.**
이번엔 순서를 뒤집는다. BlogHub 제작자도 MVP를 먼저 올려 반응을 봤다.

### Phase 0 — 테스트 (비용 0, 1~2시간)

```
글 한 편을 기존 플랫폼에 올려 반응을 본다.
```

| 항목 | 내용 |
|---|---|
| 소재 | RSC payload 사건 (§4-1, 이미 정리됨) |
| 플랫폼 | GeekNews (개발자 유입), Velog |
| 판단 기준 | 조회수·댓글·저장. **반응이 있으면 진행, 없으면 중단** |

**이 단계에서 멈춰도 손실은 2시간이다.**

### Phase 1 — 축적 (반응 있을 경우)

- 기존 플랫폼에 3~5편 추가
- 어떤 주제가 반응이 좋은지 실측
- 이 단계까지 **비용 0, 자체 사이트 없음**

### Phase 2 — 자체 사이트

- Phase 1에서 반응이 확인된 주제로 좁혀 구축
- Next.js + ISR + Vercel
- 기존 글을 이전하고 원본에는 링크 남김

### Phase 3 — AdSense

- 페이지 30~50편 확보 후 신청
- 픽앤조이와 달리 **전부 1차 경험 기반**

### Phase 4 — 확장 (선택)

- 남들의 실패 기록을 모으는 **허브**로 확장
- 단 원천이 생겼을 때만. 지금은 쓰는 사람이 거의 없다
